# 品質・テスト

[English](quality-and-testing.md)

## 1. 非機能要件

### NFR-01 品質保持

- 映像・音声のエンコーダを起動しない。
- 出力の映像・音声コーデック情報が入力と一致する。
- パススルーファイルは、厳密検証有効時にSHA-256が一致する。

### NFR-02 性能

- 10,000ファイルを含むフォルダでもUI操作をブロックしない。
- ファイルコピーおよび結合はストリーミング処理し、動画全体をメモリへ読み込まない。
- メモリ使用量は並列数に対して概ね一定とする。

### NFR-03 安全性

- 入力を変更しない。
- 出力を暗黙に上書きしない。
- 一時ファイルと完成ファイルを区別する。
- パストラバーサル、コマンドインジェクション、シンボリックリンクによる意図しない書き込みを防止する。
- Electronの権限を最小化する。

### NFR-04 対応環境

- Windows 11 x64
- macOSの現行サポート対象版（Apple Siliconを優先、Intelは配布判断時に確定）
- Ubuntu LTS x64

正式な対応OSとCPUは、CIおよび実機試験環境を確保できた組み合わせに限定する。

### NFR-05 サプライチェーン安全性

- 同一の `yarn.lock` からimmutable installで再現可能なインストールを行う。
- Yarn依存のinstall-timeスクリプトを暗黙に実行しない。
- CIの第三者Action、Go依存、同梱バイナリを変更可能な参照へ追従させない。
- 通常のPR検証にリリース秘密を渡さない。
- リリース成果物から、使用した依存と同梱バイナリのバージョンおよびチェックサムを追跡できる。

## 2. 受け入れ基準

### AC-01 複数チャプター

同一キャプチャのGoPro MP4を3本指定した場合、順番どおりの1本のMP4が生成され、映像・音声の再エンコードがなく、出力にGPMFの`GYRO`が存在する。

### AC-02 単独ファイル

1本だけの撮影グループはメディアツールを通さずコピーされ、SHA-256厳密検証を有効にした場合に入力と出力が一致する。

### AC-03 並列処理

独立した4撮影グループと最大並列数2を指定した場合、同時に実行されるグループが2を超えず、各グループ内のチャプター順序が維持される。

### AC-04 部分失敗

1グループが破損していても、他の独立グループは処理を完了し、結果レポートに成功と失敗が個別に記録される。

### AC-05 入力保護

成功、失敗、キャンセルのすべてで入力ファイルの内容、名前、配置が変更されない。

### AC-06 GPMF欠落防止

入力にGPMFがあるのに出力から欠落した場合、アプリは成功表示せず、検証失敗として報告する。

### AC-07 Yarnサプライチェーン保護

lockfileとmanifestが不整合な場合にCIが失敗し、依存のinstall-timeスクリプトは既定で実行されない。リリース成果物には成果物チェックサム、同梱ネイティブツールのバージョンとチェックサムが付随する。Yarn対応SBOM生成は選定後に追加する。

### AC-08 撮影日時による出力整理

撮影日フォルダ作成と元動画コピーを有効にした場合、指定した日付形式（既定値 `{YYYY}-{MM}-{DD}`）のフォルダに同じ日の完成動画と `original` 内の元動画が生成され、入力の内容、名前、配置は変更されない。波括弧付きトークンのカスタム形式が正しく展開され、安全でない形式が拒否されることも確認する。完成動画のコンテナ内撮影日時とファイル更新日時は先頭チャプターの撮影日時と一致し、対応OSではファイル作成日時も一致する。日時取得元と設定できなかった項目はレポートへ記録される。

## 3. テスト方針

- Goのグループ判定、順序決定、命名、衝突回避を単体テストする。
- 撮影日時の取得優先順位、撮影日フォルダへの集約、`original` コピー、日時引き継ぎをOS別にテストする。
- JSON Linesプロトコルを契約テストする。
- Nodeから実バックエンドを起動し、正常応答に加えて壊れたJSON、プロトコル不一致、未知コマンド後も通信を継続できることを確認する。
- Rendererが改変した入力パス、未解析グループ、異なる出力先をバックエンドが拒否することをテストする。
- レポート生成を無効にした場合、JSONレポートが作成されないことをテストする。
- H.264/H.265、通常色/HDR、異なるGoPro世代のサンプルで結合試験する。
- 入出力の全パケットSHA-256を比較し、GPMFのキー、時間範囲、パケット数、payloadを照合する。
- Gyroflowなど主要な後工程アプリで出力を読み込む実機試験を行う。
- Windows、macOS、LinuxのCIでビルドし、各OSでスモークテストする。
- 全体CIはPRとリリースビルドで実行する。`main`へのマージ後には通常CIを重複実行せず、ブランチ保護で最新ベースに対するPR必須チェックを要求する。リリース制御用のmain-push時のRelease Pleaseは維持する。
- CIの各OS上でElectronランタイム、UI、同一OS向けGoバックエンドを配布ディレクトリへ組み立て、パッケージ済みアプリを `--smoke-test` で起動する。
- 数千ファイル、長時間動画、低空き容量、キャンセル、異常終了を試験する。
- `package.json` とlockfileの不整合、未承認install-timeスクリプト、high/critical脆弱性をCIで検出する。
- GitHub Actionsが完全なcommit SHAへ固定され、workflow権限が明示されていることをレビューする。
- リリース時にSBOMと全同梱バイナリのチェックサムを照合する。

## 4. 実装フェーズ

1. 技術検証: 実GoPro素材でFFmpegによるストリームコピー、ffprobe、GPMF検証方法を確認する。
2. Pocket 4検証: 未編集の連続分割を固定版mp4-mergeで結合し、HEVC・2本の音声・2本のDJIデータについて全ストリーム構成と連結済み全パケットpayloadを照合する。先頭の添付画像と`tmcd`ペイロードが不変であること、章間タイムコードの連続性を確認したうえで延長したサンプル時間が結合映像全体を覆うことも検証する。
3. Go CLI: 走査、グループ化、結合、コピー、検証、レポートを実装する。
4. Electron MVP: フォルダ選択、解析結果、実行、進捗、キャンセルを実装する。
5. クロスプラットフォーム配布: OS別バイナリ同梱、署名、パッケージ作成を行う。
6. 実機互換性試験: カメラ世代、コーデック、HDR、長時間素材を確認する。
